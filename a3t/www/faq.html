A1 I am responsible for keeping agent costs under control as usage grows.
My agents…

send every request to a frontier LLM, so the bill grows with traffic and I can’t predict it.

How A3T helps

Every request starts at AgentLM’s gate. The first layers of the model read the request and decide: answer directly, think first, or escalate. If agent memory has no procedure, evidence or concept that matches, it escalates no matter what the model thinks. Because the gate is the model’s own first layers, a request it keeps costs nothing extra, and one it escalates costs a fraction of a single pass.

  1. Gate first. Small heads on the early layers estimate whether AgentLM can solve the request, which skills it needs and how much thinking it deserves.
  2. Memory coverage is a hard veto. No matching knowledge in agent memory means escalate. The model can’t talk itself into a guess.
  3. Solve locally. Kept requests continue through the same pass on a GPU in your tenant. No per-token bill from a third party.
  4. Escalate with context. When it escalates, the frontier LLM gets the request plus the context AgentLM gathered, and the answer comes back through the same checks.

What changesFrontier spend tracks the hard cases, not total traffic. The escalation threshold starts high and comes down only as measured accuracy allows.

A2 I am responsible for agents that hold long conversations and long-running cases.
My agents…

forget context, or I keep re-sending ever-longer prompts and pay for the same tokens again on every turn.

How A3T helps

AgentLM doesn’t re-read the conversation each turn. A session is a fixed-size state plus a short window of recent text, saved to agent memory after every turn and restored on the next. Knowledge isn’t pasted into the prompt either: AgentLM attends to memory directly, using attention blocks precomputed from the knowledge graph.

  1. Fixed-size session state. Most of AgentLM’s layers keep a fixed-size state instead of a growing cache. The session costs the same on turn 500 as on turn 5.
  2. Recent text, exactly. A sliding window keeps the last few thousand tokens verbatim, for exact recall of what was just said.
  3. Memory as attention, not prompt. Knowledge-graph nodes are precomputed into attention blocks stored in agent memory. AgentLM attends to the ones it needs.
  4. Saved every turn. The session snapshot is written back to memory, so a session survives restarts and can move between GPUs.

What changesEach turn processes only its new tokens. Long sessions stop getting slower and more expensive.

A3 I am responsible for giving agents the knowledge they need.
My agents…

depend on retrieval plumbing — chunking, vector search, stuffing text into the prompt — that misses facts or crowds out the question.

How A3T helps

AgentLM doesn’t need knowledge pasted into its prompt. The knowledge graph in agent memory is precomputed into attention blocks that the model reads directly through dedicated memory-attention layers. The prompt stays short, and the knowledge is part of the same pass.

  1. Precomputed once. Knowledge-graph nodes — cases, procedures, concepts — are turned into attention blocks for this model and stored next to the source records in agent memory.
  2. Selected by the gate. The gate picks the part of the graph that matters for this request, so only relevant blocks are loaded.
  3. Attended, not pasted. Memory-attention layers read those blocks directly. The prompt stays short and the question keeps its place.
  4. Source stays the truth. Records and the graph remain the source of truth; blocks are recomputed when the data or the model changes.

What changesNo chunking pipeline to tune and no context window to ration. The model works from the same knowledge your agents store.

A4 I am responsible for turning model output into actions.
My agents…

return free text or half-valid tool calls that I have to parse, validate and retry.

How A3T helps

AgentLM answers with a workflow, not prose. Decoding is constrained by the CNCF Serverless Workflow schema, so every token keeps the output valid, and A3T dry-runs the workflow before returning it. What you receive is something you can inspect, approve and run.

  1. Schema-constrained decoding. The model can only emit tokens that keep the output a valid workflow. No parsing, no repair loop.
  2. Dry run before return. A3T checks the workflow against its inputs, tools and policies without side effects.
  3. Reviewable. The result is YAML you can read on the canvas and diff in Git, like any other workflow.
  4. Same runtime. Once approved, it runs with checkpoints, policy checks and audit, like a hand-written flow.

What changesAgent output stops being a string to interpret and becomes a checked plan you can run.

A5 I am responsible for answers people can trust.
My agents…

guess confidently when they don’t know, and nothing tells me it was a guess.

How A3T helps

AgentLM doesn’t answer from nowhere. Before it commits, the gate checks whether agent memory holds a matching procedure, evidence or concept. If nothing matches, it escalates, whatever the model itself thinks. It can also escalate mid-thought when a step needs knowledge it doesn’t have.

  1. Coverage check first. The gate looks for near-matching procedures, evidence and concepts in memory for this request.
  2. Hard veto. No coverage means escalate. The model’s own confidence can’t override it.
  3. Escalate mid-thought. While reasoning, AgentLM can call escalation as a tool when a step needs knowledge it doesn’t have.
  4. A threshold you control. The escalation threshold starts high and comes down only as measured accuracy allows.

What changesAnswers are grounded in what your memory actually holds, and gaps show up as escalations you can see instead of confident guesses.

A6 I am responsible for what data leaves the company.
My agents…

send prompts full of customer and internal data to an external model on every call.

How A3T helps

AgentLM runs on a GPU inside your tenant, so most requests are answered without any data leaving it. Escalation to a frontier LLM is an action like any other: Cedar decides whether it may happen and what may be sent, and every escalation is recorded with what was sent and why.

  1. Local by default. AgentLM, agent memory and the session state all live in your tenant.
  2. Escalation is an action. The llm:escalate action is checked like a tool call: by agent, by user, by data classification.
  3. Forbid what must stay. A forbid policy can keep restricted data local whatever the model decides; AgentLM then answers or hands over to a person.
  4. Recorded. Each escalation is stored as a decision record next to the run: who, what was sent, which policy allowed it.

What changesYou decide what may leave, per agent and per data class, and you can prove what did.

A7 I am responsible for explaining what agents did.
My agents…

give answers I can’t trace. I don’t know what they knew, or why they asked an outside model.

How A3T helps

Every AgentLM answer is tied to the run that produced it. A3T records which memory the model read, whether the gate kept the request or escalated it and why, what was sent if it escalated, and the workflow that resulted. All of it sits in the execution graph next to the policy decisions.

  1. Memory read. The memory loaded for the request is recorded with the run.
  2. Gate decision. Kept or escalated, with the coverage result that decided it.
  3. Escalation record. What was sent, to which model, and which policy allowed it.
  4. One graph. The answer, the workflow it became and every decision sit in the same execution graph, queryable with AQL.

What changesFor any run, you can answer “what did it know, and why did it do that?”

A8 I am responsible for who can see which data.
My agents…

could leak data through the model. It may have seen records the person asking isn’t allowed to see.

How A3T helps

AgentLM only reads memory the request is allowed to see. Before any attention blocks are loaded, Cedar checks the agent, and the user it acts for, against each memory scope. Blocks from scopes they can’t read are never loaded, so the model can’t draw on them.

  1. Scopes on memory. Memory is organised by tenant, team and agent namespace, each covered by policy.
  2. Checked before loading. Cedar decides which scopes this agent, acting for this user, may read — before any block reaches the GPU.
  3. Nothing to leak. Blocks from denied scopes are never loaded, so they can’t influence the answer.
  4. Logged. Every allow and deny for memory access is in the decision log.

What changesThe model never knows more than the person it’s working for.

AgentLM’s output is a workflow, and a workflow does nothing until it passes A3T’s checks. It is dry-run first, then every step is checked by Cedar as it runs, and steps you mark as sensitive wait for a human approval.

  1. A plan, not an action. The model produces a workflow. Nothing touches your systems at this point.
  2. Dry run. Inputs, tools and policies are checked without side effects.

A10 I am responsible for running models at predictable cost and latency.
My agents…

depend on a frontier API whose latency, rate limits and price I don’t control, and fine-tuning a model per team is out of reach.

How A3T helps

AgentLM is a 4–8B-parameter model that runs on a single GPU, served by vLLM. Session memory per user is fixed in size, so capacity planning is arithmetic. New domains come as small skill adapters stored in agent memory and paged onto the GPU when the gate asks for them, so teams don’t need their own fine-tuned model.

  1. One GPU per model. No cluster of accelerators per tenant. Start with one GPU and add more as traffic grows.
  2. Fixed per-session memory. Tens of megabytes per session whatever its length, so a GPU’s capacity is a known number.
  3. Skills paged in (roadmap). Domain and tenant skills are adapters trained against one frozen core, cached on the GPU and evicted when cold.
  4. Versioned core. The core model changes rarely and deliberately. On an upgrade, memory’s attention blocks are recomputed from the source data as a background job.

What changesLatency and cost you can plan, on hardware you control, without a model per team.

A11 I am responsible for GPU capacity.
My agents…

use more GPU memory the longer a conversation runs, so long sessions and many users don’t fit.

How A3T helps

Most of AgentLM’s layers are recurrent: they keep a fixed-size state instead of a cache that grows with every token. A few attention layers keep a short sliding window for exact recall of recent text. Per session, memory stays at tens of megabytes however long it runs.

  1. Fixed-size state. Recurrent layers carry the session forward in constant memory.
  2. A short exact window. Attention layers keep only the last few thousand tokens verbatim.
  3. Older knowledge lives in memory. Anything outside the window is read from agent memory through memory attention, not held in GPU cache.
  4. Capacity is arithmetic. Sessions per GPU is a number you can plan, not one that shrinks as conversations grow.

What changesLong sessions and many concurrent users fit on the GPUs you have.

A12 I am responsible for keeping agent sessions running through restarts and scaling.
My agents…

lose their session when a GPU node restarts, and I can’t move a session to another node.

How A3T helps

After every turn, AgentLM’s session — its fixed-size state, the recent-text window and pointers to the memory it used — is saved to agent memory as a snapshot. The next turn restores it on whichever GPU picks it up.

  1. Snapshot every turn. The session is written to agent memory after each answer.
  2. Restore anywhere. Any GPU serving the same model version can load it and continue.
  3. Survives restarts. A node restart or rescheduling costs one restore, not the conversation.
  4. Scale freely. Sessions aren’t pinned, so you can add, drain or replace GPUs without stranding users.

What changesGPU nodes become replaceable. Sessions live in memory, not on a machine.

W1 I am responsible for shipping agents that do real work, not just chat.
My agents…

call the LLM for steps that should be plain code, so every run is slow, costly and a little different.

How A3T helps

An A3T agent is three parts working together: a workflow, AgentLM and memory. The workflow carries the known path with typed inputs and deterministic tasks, and its execution is monitored step by step. Only deviations from that path go to AgentLM, which uses the flow execution graph in agent memory to resolve the case and recommend how the workflow should change. If AgentLM can’t resolve it, it escalates to a frontier LLM, and only if policy allows.

  1. Typed inputs. Every workflow declares its input schema. Unexpected input is caught at the edge, not discovered by a model halfway through a run.
  2. Deterministic by default. Switches, loops, transforms, MCP tool calls and triggers run as plain tasks on the Rust runtime — no tokens spent, the same result every time.
  3. Execution is monitored. Each step is compared with the expected path. When a run leaves it — an unknown branch, a schema mismatch, an outcome out of range — only that deviation is handed to AgentLM.
  4. AgentLM manages the flow. AgentLM reads the flow execution graph in agent memory — past runs, the paths they took and how they ended — to handle the case, then recommends a workflow change. Approved, it becomes the next version.
  5. Escalate only when stuck. A case AgentLM can’t solve goes to a frontier LLM with the context it needs. Cedar decides whether it may leave your tenant, and the call is recorded.

What changesModel calls shrink to the cases that need judgement, frontier calls shrink further still, and the workflow improves from its own history instead of re-reasoning every run.

W2 I am responsible for agents that finish long, multi-step jobs.
My agents…

fail halfway through, and I have to rerun everything from the start — including steps that already had side effects.

How A3T helps

A3T checkpoints workflow state after every task. When a step fails, the run resumes from that step with its state intact; steps that already finished are not repeated.

  1. Checkpoint after each task. Inputs, outputs and the run’s position in the flow are saved as it progresses.
  2. Per-task failure policy. Each task carries its own retries, backoff and timeout, so one slow dependency doesn’t sink the whole run.
  3. Resume, don’t restart. After a failure or a restart, the run picks up at the failed step. A ticket that was already opened, or a message already sent, stays done.

What changesLong jobs survive failures and restarts without duplicate side effects or wasted compute.

W3 I am responsible for the runtime agents depend on in production.
My agents…

stall under load, and latency jumps whenever the runtime pauses — not acceptable for bidding, trading or live monitoring.

How A3T helps

A3T’s core is written in Rust. There is no garbage collector to pause execution, and tasks are dispatched in microseconds, so latency stays predictable as load grows.

  1. Any trigger in. Webhooks, schedules and events all feed the same dispatcher.
  2. Microsecond dispatch, no GC pauses. No stop-the-world pauses, and async I/O keeps workers busy instead of blocked.
  3. LLM off the hot path. Deterministic tasks and tool calls run directly. The LLM is called only on deviations (see the first question), so a slow model doesn’t set your latency.

What changesTight latency budgets — like an RTB bid window — become something you can plan for, not hope for.

P1 I am responsible for access control across the company.
My agents…

run with the same broad access as whoever deployed them.

How A3T helps

Every A3T agent has its own service identity. Before each task, the Cedar policy engine built into the runtime checks who is acting, on whose behalf, which action and which resource. Anything not explicitly allowed is denied.

  1. Agent as a principal. Each agent is a named identity in your policies, separate from the person who built it.
  2. On behalf of. When an agent acts for a user, that user’s groups are part of the decision.
  3. Checked before it runs. Every task and tool call is evaluated first. Denied actions never execute, and are logged.

What changesLeast privilege for agents, written in policy you can read.

P2 I am responsible for joiners, movers and leavers.

How A3T helps

A3T agents run as service accounts owned by groups, not by individuals. Users and groups sync from your identity provider over SCIM, so when someone leaves, their access — and any delegation to agents — is removed, while production agents keep running.

  1. SCIM sync. Users and groups come from your IdP; there is no second user list to maintain.
  2. Group-owned service accounts. Agents belong to a team, so ownership survives people changes.
  3. Delegation follows the person. Acting on someone’s behalf ends when that person’s access ends.

What changesNo orphaned agents, no lingering access, and no outage when someone moves on.
